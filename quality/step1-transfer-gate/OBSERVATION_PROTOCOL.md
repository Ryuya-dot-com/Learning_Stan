# STEP 1 独立転移・観察プロトコル

## 1. 観察する問い

次を別々に観察します。

1. 与えられた列契約と品質方針を、コードを書く前に計画できるか。
2. rawを保ち、問題行と検査済みデータを再現可能に分けられるか。
3. 正答試行、参加者、条件という1行の意味を保って切替コストを作れるか。
4. 保存物を読み直し、空のRセッションから再生成できるか。
5. 記述結果と一般化できない限界を分け、中心課題から変えた判断を説明できるか。

満足度や最終的な`TRANSFER PASS`だけでなく、初回計画、最初の成果物、支援、エラーからの修正、説明の根拠を記録します。

## 2. 対象と観察条件

- 最低3名、可能なら5名のR初学者
- L11〜L16を完了し、修了から2〜7日後を推奨
- 教材の設計・実装へ直接関与していない
- 初回提出まで`step1_analysis.R`、NB1、公開版`step1-transfer.qmd`、`step1_transfer_check.R`を開かない
- 自発的なR Helpと公式パッケージ文書は利用可能。利用しても支援なしの`I`を維持できる
- 生成AI、他者の回答、非公式な完成コードは初回提出まで利用しない

これは少人数の形成的観察です。達成率を母集団へ一般化しません。最初のコホートの結果を見てから、現版に都合のよい合格点を設定しません。

## 3. 進行役の準備

1. 対象commit SHA、公開URL、実施日時、R・RStudio・主要パッケージ版を固定する。
2. `npm run test:step1-transfer-observation-rehearsal`を実行し、配布から採点までの運用動線が`REHEARSAL PASS`になることを記録する。この結果は参加者証拠へ数えない。
3. 検証済み`participant-pack.zip`を参加者ごとの新しい場所へ展開し、そのフォルダを新しいProjectとして開く。
4. `step1_transfer_check.R`と`FACILITATOR_KEY.md`は参加者から見えない別フォルダに置く。
5. 進行役がraw MD5、行数、列名を記録し、CSVを変更していないことを確認する。
6. 成果物用の`data/processed/`と`output/`は参加者自身に作らせる。
7. 画面録画・録音はせず、匿名記録票の観察事実欄を使う。

参加者が個別配布用QMDのダウンロードチャンクを実行すると、自己チェッカーが事前露出します。規定観察ではQMDを渡さず、`PARTICIPANT_TASK.md`だけを使います。

## 4. 支援水準

各タスクで使った最大水準を記録します。

| コード | 支援 |
|---|---|
| I | 進行役の支援なし。自分で選んだ公式ヘルプ利用を含む |
| H1 | 課題文、自分の計画、直前の出力を読み直すよう中立に促した |
| H2 | 課題票の該当節、確認すべき表・列、公式ヘルプの入口を示した |
| H3 | 次の具体的な検査、関数、変形方向、修正操作を伝えた |
| F | 支援しても必須成果物または説明を完了できなかった |
| B | 端末、権限、パッケージ、時間など外部要因で実施できなかった |

7分間動きがない、または参加者が支援を求めた場合に限り、H1から順に使います。支援した時刻、実際の言葉、支援前の状態を記録します。タイプミスの読み上げも支援です。

## 5. 必須タスク

### TR01 — コード前の計画

参加者へ課題票と2つのCSVを示し、最初のコードを書く前に、入力・品質ルール・中間表・成果物・再現確認の順序を短く説明してもらいます。

記録するもの:

- 1行の意味とキー
- rawを変更しない方法
- 5種類の品質検査を行う位置
- 誤答除外と品質除外の順序
- 参加者×条件から切替コストへ変形する計画
- 保存後の再読込とfingerprint確認

関数名の正確さだけでは判定しません。品質検査より先に平均を作る、rawを修正して問題を消す、group平均から参加者差を作る計画は、そのまま観察事実として残します。

### TR02 — 品質ゲートとraw保全

参加者が`step1_transfer.R`を作り、rawを読み、列契約・キー・5品質ルールを検査し、問題一覧と検査済みデータを保存します。

進行役は途中の正誤を伝えません。参加者が完了を宣言した時点で、問題一覧、検査済み表、raw MD5、上書きの試行を記録します。既知件数はまだ伝えません。

### TR03 — 参加者別切替コスト

検査済みデータから正答試行だけを残し、参加者別に`repeat`と`switch`の平均を作り、`switch - repeat`を計算して保存してもらいます。

記録するもの:

- 誤答除外の位置
- 参加者×条件の行数確認
- 横長変換前後の1行の意味
- 差の向き
- 参加者を潰して全体平均だけにしていないか

### TR04 — 結果メモと再現

分析対象、記述結果、解釈の限界を3行で保存し、Rを再起動したつもりでスクリプトを上から再実行してもらいます。少なくとも作業オブジェクトを削除し、成果物を別名退避または削除してから再生成します。削除操作は観察用Project内の4成果物だけを正確に対象とし、rawは削除しません。

初回提出として、4成果物、raw MD5、再実行結果、参加者の完了宣言時刻を固定します。

### TR05 — 説明とチェッカー後の修正

初回提出を記録した後で、進行役が`step1_transfer_check.R`をProject直下へコピーし、参加者に自己チェッカーを1回実行してもらいます。初回の`PASS`またはエラー全文の個人情報を除いた要約を記録します。

失敗した場合は、期待値を口頭で教えず、チェッカー出力と自分の中間表を根拠に1回だけ修正できます。初回と修正後を混ぜません。その後、参加者に次を説明してもらいます。

- 中心課題から再利用した判断
- 列名・条件名・1行の意味に応じて変えた箇所
- データ内で記述できる結果
- 4名の合成パイロットから一般化できないこと
- 次の実データで、分析前に依頼者へ確認する規則

## 6. 結果カテゴリー

これは成績ではなく、観察条件を記述するカテゴリーです。

- `INDEPENDENT`: TR02〜TR04をIまたはH1で初回提出し、rawを保ち、初回チェッカーがPASS
- `SELF_REPAIRED`: 初回チェッカーは失敗したが、期待値の提示なしに1回の自己修正でPASS
- `SUPPORTED`: H2またはH3を使ってPASS、または主要説明が支援後に成立
- `INCOMPLETE`: 必須成果物、再現、限定付き解釈のいずれかが未完了
- `BLOCKED`: 外部要因で判定不能
- `INVALID`: 解答・チェッカーの事前露出または誘導により初回条件が崩れた

一人の総合カテゴリーだけで原因を決めず、TR01〜TR05別の支援水準と観察事実を残します。

## 7. 修正先の切り分け

| 観察 | 最初に確認する箇所 | すぐ教材を増やさないための反証 |
|---|---|---|
| TR01で品質検査より先に集計する | L12→L13接続、L16の再現手順 | 課題票の順序が曖昧でないか |
| TR02で列名置換だけを行い問題行が残る | L13のルール一般化、NB1 | CSV配布や型推論の環境差でないか |
| TR03で全体平均1行にする | L14のgroup単位、L16の差の意味 | 課題票が参加者別と明記しているか |
| TR04で手操作を再現できない | 保存・再読込・スクリプト導線 | 権限や作業ディレクトリの問題でないか |
| TR05で群効果を結論する | ケースカードと結果メモ例 | 「training_group」が推論を誘発していないか |
| チェッカーだけを期待値へ合わせる | エラー読解と成果物確認 | チェッカーのメッセージが答えを露出していないか |

## 8. 観察終了後

参加者別記録からコホート判断票を作ります。同じ失敗が複数名に出ても、人数だけで原因を確定しません。観察事実、参加者の説明、環境証拠、反証を並べ、次版で変える箇所を原則1つに絞ります。raw消失、品質検査なしの分析、再現不能な除外、4名からの過剰な一般化はP1候補として独立レビューします。
