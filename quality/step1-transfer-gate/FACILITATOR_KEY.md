# 進行役用の準備・採点キー

参加者へ初回提出前に見せません。この文書は特定のdplyrコードを要求する解答例ではなく、入力データと成果物の契約、観察条件、原因の切り分けを固定します。

## 1. 配布前検査

`participant-pack.zip`を新しい場所へ展開します。Projectには最初に次だけが入ります。

```text
PARTICIPANT_TASK.md
data/
└── transfer/
    ├── switch_trials_dirty.csv
    └── switch_participants.csv
```

公開スターターZIPをそのまま渡すと、完成版スクリプト、NB1、公開版転移課題、自己チェッカーが見えるため規定観察には使いません。入力CSVは公開物からバイト単位でコピーし、改変しません。

配布前に`npm run test:step1-transfer-observation-pack`を実行し、3ファイル限定、元ファイル一致、期待値非露出、再生成一致を確認します。

続けて`npm run test:step1-transfer-observation-rehearsal`を実行します。`REHEARSAL PASS`は、ZIP展開後の相対パス、raw保全、初回提出前のチェッカー不在、提出後のチェッカー追加と採点が動くという運用証拠です。R処理は採点動線用fixtureであり、初心者の解答や転移の証拠ではありません。

進行役の事前確認:

- raw MD5: `55e3056af5bda9a8cf86c19df9b0ad6f`
- 試行表: ヘッダーを除いて21入力行
- 参加者表: 4名、`participant_id`は一意
- 試行列: `participant_id`, `trial_type`, `response_ms`, `is_correct`, `block`
- 参加者列: `participant_id`, `training_group`, `age`

## 2. 品質ゲートの期待契約

既知問題は次の5行で、各ラベルが1件です。

| issue | 該当する特徴 |
|---|---|
| `duplicate` | A01・repeat・410ms・正答・block 1の完全重複 |
| `invalid_trial_type` | `trial_type`が`practice` |
| `response_out_of_range` | `response_ms`が50 |
| `unknown_participant` | `participant_id`がA99 |
| `missing_correct` | `is_correct`が欠損 |

期待成果物:

- `switch_trials_issues.csv`: 5行、元の5列と`issue`
- `switch_trials_checked.csv`: 16行、元の5列
- checked内の正答試行: 14行
- raw MD5: 作業前後で同一

問題行の出力順は問いません。ラベルだけを5つ書いた表、元行の値が異なる表、rawを直接修正して問題を消した表は契約を満たしません。複数の問題に該当しうる行が将来追加された場合は優先順位を事前に版管理しますが、現データでは各問題行を一意に分類できます。

## 3. 集計の期待契約

正答試行だけを使った参加者別平均と差は次です。

| participant_id | repeat | switch | switch_cost_ms |
|---|---:|---:|---:|
| A01 | 420 | 500 | 80 |
| A02 | 400 | 500 | 100 |
| A03 | 440 | 540 | 100 |
| A04 | 415 | 525 | 110 |

`switch_cost_ms`は`switch - repeat`です。全参加者を1行へ潰す、誤答を平均へ含める、`repeat - switch`にする、`training_group`別効果を推定する処理は依頼と異なります。

参加者属性表の`age`欠損は、今回の切替コスト計算には使いません。欠損を見つけて説明できれば記録しますが、A04を試行データから除く理由にはしません。`training_group`は記述的な属性であり、4名から群効果を結論しません。

## 4. 結果メモの期待契約

3行がそれぞれ次で始まることを確認します。

- `分析対象:` — 検査済みデータの正答試行だけを参加者×条件で要約したこと
- `記述結果:` — 4名全員でswitch平均がrepeat平均より高く、切替コストが80〜110msだったこと
- `解釈の限界:` — 4名の合成パイロットなので母集団へ一般化せず、群差も結論しないこと

完全一致の日本語は要求しません。数値、対象、方向、限界が区別されていれば受理します。ただし公開自己チェッカーは機械判定のため、指定した接頭辞と`正答試行`、`4名全員`、`一般化`を要求します。チェッカー仕様による失敗と、統計的な誤解を別々に記録します。

## 5. 初回提出の固定

参加者が完成を宣言したら、チェッカーを渡す前に次を記録します。

1. 4成果物の存在、列名、行数
2. rawの作業後MD5
3. `step1_transfer.R`を空の作業環境から実行できたか
4. 参加者が説明した対象、方向、限界
5. TR01〜TR04で使った最大支援水準
6. 完了宣言時刻

成果物やコード全文をリポジトリへ保存する必要はありません。必要な場合も個人パス、ユーザー名、研究室固有情報を除き、参加者の同意と保管方針を確認します。

## 6. 自己チェッカー

初回提出を固定した後だけ、公開版`public/challenges/step1_transfer_check.R`と同じファイルをProject直下へコピーします。参加者が次を実行します。

```r
source("step1_transfer_check.R", encoding = "UTF-8")
```

期待する最終表示は`TRANSFER PASS`です。初回失敗では、エラー種別を次に分類します。

- `PATH`: 保存先・作業ディレクトリ
- `SCHEMA`: 列名・列順・型
- `QUALITY`: 問題行またはchecked行
- `SUMMARY`: 正答除外・group単位・差の向き
- `NOTE`: 対象・結果・限界または機械書式
- `RAW`: fingerprint不一致
- `ENV`: パッケージ・権限・文字コード

参加者へ期待件数や期待値を口頭で伝えません。チェッカーの出力と自分の中間表を使う1回の修正だけを認め、初回結果を上書きしません。

## 7. 支援と判定の注意

- base Rやdata.tableなど別の書き方でも、同じ成果物契約と説明を満たせば受理する。
- 自分で公式文書を探す行動は`I`。進行役が場所を示すとH2、具体的関数を示すとH3。
- タイプミスと品質概念の誤りを分ける。ただし進行役がタイプミスを示した支援は記録する。
- 最終PASSを初回の独立完遂へ読み替えない。`INDEPENDENT`、`SELF_REPAIRED`、`SUPPORTED`を区別する。
- 自信、満足度、所要時間の短さだけを転移の証拠にしない。
- raw上書き、品質検査なしの集計、再現不能な手操作、4名からの群効果一般化はP1候補として独立レビューする。
- パッケージ不足、Windowsのファイルロック、作業ディレクトリ、権限は`B`または`ENV`として教材理解と分ける。

- [ ] 初回チェッカー結果と修正後を分けた
